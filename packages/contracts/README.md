# Versioned API and event contracts

`openapi.json` is OpenAPI 3.1 for the runnable test milestone, version 0.1.0. `events.schema.json` describes durable participant-authorized event envelopes. Both are generated from `build-contract.mjs`: run `node packages/contracts/build-contract.mjs`, or `node packages/contracts/build-contract.mjs --check` to reject drift.

Backend integration tests validate actual HTTP responses against these schemas. Removing/renaming a required response field or changing a call-state value fails the contract check. Change the contract and consumer together and raise the API version for incompatible released changes.

Flutter uses the checked-in SDK in `dart/`, generated by **OpenAPI Generator 7.26.0** with the official stable `dart` generator and native serialization. Its existing `NightShiftApi` facade dispatches requests through generated operations and models, while retaining runtime base URLs, bearer authentication, idempotency keys, structured errors and a total request deadline. Presentation models remain separate. The official native generator fits the existing `package:http` transport and avoids a second Dio/build-runner stack. The generated SDK requires `http` 1.5.0 for abortable requests and compiles with the pinned Flutter 3.27.4/Dart 3.6.2 toolchain.

## Reproducible generation

From the repository root, with pinned Node and Java 17+ installed:

```sh
npm run generate:client
npm run check:client
npm run check:mobile
```

Edit `build-contract.mjs`, regenerate the canonical JSON with `npm run generate --workspace @nightshift/contracts`, then generate/review the SDK and update callers/tests together. `generate:client` first checks that canonical JSON is current. `check:client` runs the same pinned generator in a temporary directory and fails on missing, extra or changed SDK files. CI runs this check; ordinary Flutter/API builds use the checked-in SDK without invoking the generator. Android builds still require their normal JDK/Gradle toolchain. Do not hand-edit `dart/` or move charge computation to Dart.

The script downloads the pinned JAR from Maven Central into ignored `artifacts/openapi-generator/` and verifies its hard-coded SHA256 before execution, including cached JARs. Initial generation needs network access; later generation can run from the verified cache. Set `JAVA_HOME` or put Java on PATH. No credentials are needed or embedded. The script normalizes LF line endings and excludes generator metadata with machine-specific paths; it does not require a Dart formatter to regenerate byte-identical sources.

OpenAPI Generator's OpenAPI 3.1 support is beta. Compatibility is checked against this actual contract, including required nullable values, enum values, literal boolean constants, integer financial units and actual POST 201 responses. The small versioned [template overrides](generator/README.md) keep required/type checks active in release, fix boolean-constant rendering and redact diagnostic strings. The generated client is **not a complete JSON Schema validator**: backend validation and contract integration tests remain authoritative for formats, bounds and additional-property rules.

Flutter tests reject missing fields, unknown modes/languages, invalid integers and malformed nullable objects/dates. They verify credential redaction, runtime URLs, encoded cursors, stable mutation headers, non-JSON errors, and deadlines covering both connection and body streaming. Run `npm run smoke:client` from the root with Node/Flutter on PATH to exercise generated SDK operations against a running test backend. The wrapper loads the ignored local environment and passes credentials through the process environment. A successful HTTP journey does not establish audible RTC media or provider-side cutoff.

Calls accept no price, elapsed duration, arbitrary RTC channel or participant UID from a client. New calls require the test quote ID and an `Idempotency-Key`. Lifecycle actions require the last observed `expectedVersion`; after `STALE_VERSION` retrieve the current call and retry with a fresh key. Replaying the same actor/operation/key/body returns the original response, while reuse with a different body returns `IDEMPOTENCY_CONFLICT`.

The only modes are `customer` and `listener`. Account approval is a server entitlement; there is no staff mode or self-approval endpoint in the mobile API.
